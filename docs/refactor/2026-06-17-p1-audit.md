## A. Real bugs

The 4 fix cards from 2026-06-16 are **all still open**. R0.3
(commit `5873057`) only wired the new validators into **POST**
`/api/projects`, **POST** `/api/pins`, and **POST** `/api/projects/[id]/subscribers`.
The 4 PATCH/DELETE/POST routes flagged by the prior audit were not
touched.

### A1. `PATCH /api/projects/[id]` does NOT call `validateProjectName`
**File:** `src/app/api/projects/[id]/route.ts:77-79`
**Reported in:** t_0ede5506
**Confirmed:** YES — bug is present and live.

```ts
// Line 77-79
if (name !== undefined && (typeof name !== 'string' || name.length === 0 || name.length > 200)) {
  return NextResponse.json({ error: 'name must be a non-empty string ≤200 chars' }, { status: 400 });
}
```

The route inlines a 3-clause ad-hoc check. Compared to the
centralised `validateProjectName` in `src/lib/validation.ts:118-126`,
it's missing the **null-byte rejection** and the **explicit
"must not contain null bytes"** error message. A payload of
`{ "name": "foo\u0000bar" }` would pass this inlined check, hit the
DB, and produce a Postgres error that bubbles up as a 500. Worse, the
inlined check returns the same generic message for "not a string",
"empty", and "too long" — three different user errors, one
indistinguishable 400. R0.3 *added* `validateProjectName` to
`lib/validation.ts` (line 118) and *wired it into POST /api/projects`
(line 73). The PATCH route was not updated.

**Why it matters:** the centralization was the *whole point* of R0.3
per the plan ("Replace the inline validators in the routes"). PATCH
is the operator-side path — a typo'd or null-byte-laden rename is
exactly the input shape R0.3 was meant to defend. A 500 on
`PATCH /api/projects/[id] {"name":"x\u0000y"}` is also an
information leak (DB error surfaces in the catch).

**Fix plan:** in `src/app/api/projects/[id]/route.ts`, replace the
inlined check (lines 77-79) with `const nameRes = validateProjectName(name); if (!nameRes.ok) return NextResponse.json({ error: nameRes.error }, { status: 400 });`. The
`name` variable can stay un-typed (`string | undefined`) because
`validateProjectName` is already typed `(name: string)`; the route
should do `if (name !== undefined) { const r = validateProjectName(name); ... }` to preserve the "name is optional" semantics
that the inlined check has. Add a test in
`tests/integration/projects-id.test.ts` that sends
`{ name: 'x\u0000y' }` and expects 400 with the null-byte error
message. ~6 LOC, ~12 LOC of test.

### A2. `PATCH/DELETE /api/pins/[id]` do NOT validate the id as a UUID
**File:** `src/app/api/pins/[id]/route.ts:17, 41`
**Reported in:** t_2554bb58
**Confirmed:** YES — bug is present and live.

```ts
// PATCH line 17
const { id } = await params;
// PATCH line 22-25
const pin = await prisma.pin.update({
  where: { id },
  data: { status },
});
// DELETE line 41
const { id } = await params;
// DELETE line 44-48
const pin = await prisma.pin.findUnique({ where: { id }, ... });
```

The route goes straight from path-param to prisma. With an id like
`"not-a-uuid"`, prisma's `where: { id }` throws a P2009 / P2010 / P2023
parse error (the exact class depends on the prisma version); the
catch block at line 27-30 / 75-78 swallows it as a generic
**500 — "Failed to update pin" / "Failed to delete pin"**.

By contrast, **sibling routes already have the guard:**
- `recapture/route.ts:23` calls `validateScreenshotId(id)` and
  returns 400 on bad shape (line 24).
- `status/route.ts:32-33` does the same.
- `image/route.ts` does NOT — it just does `prisma.screenshot.findUnique({ where: { id } })`. That's a separate smaller
  bug (different fix card) but not on this audit's checklist.

There is **no `validatePinId` in the lib** — the closest is
`validateScreenshotId` (line 84), which is a UUID-only check. The Pin
model's `id` is a Prisma `cuid()` (not a UUID) per the schema. So
this is two sub-issues:
1. **Defensive 400 vs leaky 500** — the bug as filed. Fix:
   add a `validatePinId(id)` to `lib/validation.ts` that accepts the
   cuid shape (`/^c[a-z0-9]{24,30}$/i`), wire into both handlers.
2. **No validator exists** — needs to be added to the lib first.

**Why it matters:** every malformed-id PATCH/DELETE is a free
500. The dashboard UI will surface "Failed to update pin" with no
signal that the id was the problem, leading to "did the DB break?"
support questions. Also: a burst of malformed requests against this
endpoint would generate a stack of prisma parse errors in the log
and a noise spike on the error rate.

**Fix plan:** in `src/lib/validation.ts`, add `validatePinId(id)` and
`validateProjectId(id)` (cuid for Project, cuid for Pin — both are
Prisma `cuid()` ids per the schema). In
`src/app/api/pins/[id]/route.ts`, insert the guard after
`const { id } = await params;` in both PATCH and DELETE:
`const idRes = validatePinId(id); if (!idRes.ok) return NextResponse.json({ error: idRes.error }, { status: 400 });`.
Tests: add 2 cases to `tests/integration/pins.test.ts` (one PATCH,
one DELETE) that POST with `id="garbage"` and expect 400 + no
prisma call. ~30 LOC across 3 files. Also wire `validateScreenshotId`
into `image/route.ts` while we're here — it's the same fix pattern,
already a partial regression, not on the explicit checklist but
should not be skipped.

### A3. `POST /api/pins/[id]/comments` does NOT validate `text` via `validatePinText`
**File:** `src/app/api/pins/[id]/comments/route.ts:31-33`
**Reported in:** t_b5b37fc9
**Confirmed:** YES — bug is present and live.

```ts
// Line 30-33
const { text, author, authorRole } = await req.json();
if (!text) {
  return NextResponse.json({ error: 'text required' }, { status: 400 });
}
```

The route only checks "text is truthy". It does not enforce:
- Length cap (LIMITS.PIN_TEXT_MAX = 2000)
- Null-byte rejection
- Trim-then-validate (so a comment of "   " passes the truthy check
  and lands in the DB as 3 spaces)

`validatePinText` (in `validation.ts:237-249`) was added in the R0.3
commit and **wired into the pin-create flow**
(`src/app/api/pins/route.ts:68`). The comment-create flow at
`/api/pins/[id]/comments` was not updated. Note the contrast: the
initial pin creation goes through `validatePinText`, but a
follow-up comment on the same pin does not. An attacker can post
20KB of `aaaa...` as a follow-up comment; the initial pin can only
hold 2KB.

Also, `author` / `authorRole` are not validated at all — they can
be arbitrary strings. Not on the explicit checklist, but the same
R0.3 pattern would catch them.

**Why it matters:** this is the dashboard's chat-like UI for
multi-turn review. A 20KB comment slows the dashboard render of
that pin's thread (the whole comments array loads on every poll —
see R0.1, 5s cadence × unbounded comment size). A whitespace-only
comment makes the dashboard look like the operator typed nothing
and pressed save.

**Fix plan:** in `src/app/api/pins/[id]/comments/route.ts`, replace
the truthy check with
`const textRes = validatePinText(text); if (!textRes.ok) return NextResponse.json({ error: textRes.error }, { status: 400 });`
and use `textRes.value` in the prisma.create. Also validate
`author` and `authorRole` with `sanitizeText` (existing in
validation.ts:72) to cap their length. ~6 LOC, ~2 tests
(`whitespace-only text → 400`, `2KB+1 → 400`).

### A4. `DELETE /api/projects/[id]/subscribers/[email]` does NOT lowercase the email
**File:** `src/app/api/projects/[id]/subscribers/[email]/route.ts:25`
**Reported in:** t_7d675698
**Confirmed:** YES — bug is present and live.

```ts
// Line 25
const { count } = await prisma.subscriber.deleteMany({ where: { projectId, email } });
```

`email` is the raw path-segment string. If the dashboard UI
(or any future curl) calls
`DELETE /api/projects/proj-1/subscribers/Alice%40Example.com`, the
DB query is
`deleteMany({ where: { projectId: 'proj-1', email: 'Alice@Example.com' } })`.
Because the corresponding POST route (R0.3 wired `validateSubscriberEmail`,
which lowercases on the way in, see
`src/app/api/projects/[id]/subscribers/route.ts:42-44`) stored
`alice@example.com`, the row is `email = 'alice@example.com'` —
**the DELETE silently matches 0 rows and returns `{ deleted: true, count: 0 }`**.

The user sees `{ deleted: true }` and thinks the subscriber was
removed. It's not — it's still in the DB. Next email campaign
still goes to them.

The control-character check at line 19-21 (added in a previous
fix) is good. The CR/LF rejection at the path layer is good. The
count: 0-vs-1 distinction is at least returned. But the
**lowercase normalization that the POST route does is missing
from the DELETE route** — exactly the bug as filed.

**Why it matters:** this is the most user-impactful of the 4 — the
operator thinks they removed a subscriber, but the subscriber keeps
getting emails. There's no visible error to surface the case
mismatch. The fix is one line.

**Fix plan:** in `src/app/api/projects/[id]/subscribers/[email]/route.ts`,
add `import { validateSubscriberEmail } from '@/lib/validation';`
and replace the raw `email` in the where clause with the
normalized form:
```ts
const emailRes = validateSubscriberEmail(email);
if (!emailRes.ok) return NextResponse.json({ error: emailRes.error }, { status: 400 });
const emailNormalized = emailRes.value;
// ... deleteMany({ where: { projectId, email: emailNormalized }, ... })
// and use emailNormalized in the audit metadata too
```
The control-character check at line 19-21 can stay (it's a
defense-in-depth for header-injection; `validateSubscriberEmail`
will also reject malformed shapes). Add a test in
`tests/integration/subscribers-email.test.ts` that sends
`Alice@Example.com` and verifies `deleteMany` was called with
`email: 'alice@example.com'`. ~4 LOC, ~1 test.

## B. P1 dispatch plan

The plan in `2026-06-15-refactor-plan.md` ships P1 in this order:
**R1.3 → R1.2 → R1.1**, and the 4 R0.3 fix cards (Section A)
**before any P1 work** because they close a 500/422 leak that the
new P1 routes would inherit.

### P1-R0.3 fix cards (ship FIRST, ~half a day)
The 4 fix cards in Section A close R0.3 gaps. They are small, low-risk,
and unblock the rest of P1. Sequence: **A4 (subscriber DELETE) → A1
(project PATCH) → A3 (comment text) → A2 (pin PATCH/DELETE)**. A4
first because it's a 1-liner with the highest user impact (silent
failure). A2 last because it requires a new validator function
(`validatePinId`, `validateProjectId`) and a small schema-shape audit.
For each, do the fix plan in Section A, run the targeted integration
test file, then `npx vitest run` for the full 259 suite. The 4 fixes
combined are ~50 LOC of route code, ~30 LOC of new tests.

### P1-R1.2 — CSRF tokens for state-changing routes
**File scope:** new `src/lib/csrf.ts`, `src/lib/auth.ts` (no
changes to `requireDashboardOrigin` itself), and 5 routes
(`/api/projects` POST, `/api/projects/[id]` PATCH+DELETE,

`/api/pins/[id]` PATCH+DELETE, `/api/pins/[id]/comments` POST,
`/api/screenshots/[id]/recapture` POST — 7 actually).

**Sequence:** First, add `src/lib/csrf.ts` with `issueCsrfToken(req)`
(set a `__Host-csrf` cookie, return the token) and
`requireCsrfToken(req)` (constant-time compare the cookie to the
`x-csrf-token` header). Then add a single `requireCsrf()` call
right after the auth check in every state-changing route. Then
issue the token in the dashboard root layout — add a server
component that issues once per session. Then update the
`dashboardHeaders()` helper in `src/lib/client-origin.ts` to
auto-attach `x-csrf-token` from a `getCsrfToken()` getter (which
reads the cookie once). Finally, add tests: for each of the 7
state-changing routes, a 401 on missing-or-mismatched token and
a 200 on the present matching pair. The 259 baseline shouldn't
drop — the existing tests don't set the token, so they'll need
to either pass an Origin AND a token, or a new test helper
`testHeaders()` that returns both. ~80 LOC + ~50 LOC of tests.

## C. New findings since the prior review

### C1. R0.1 — `?since=` polling (commit `0455b27`)
**Verified working correctly at every level.**

- **Project level** (`route.ts:25`): `where: { updatedAt: { gt: since } }` — correct. The `updatedAt` column is on the Project model.
- **Page level** (`route.ts:28`): `where: { updatedAt: { gt: since } }` — correct. Same column on Page.
- **Screenshot level** (`route.ts:33-34`): `where: { capturedAt: { gt: since } }` — correct. Screenshot has no `updatedAt` (per the route comment), so `capturedAt` is the right marker. Worth a sanity note: a Screenshot's `capturedAt` is set once at insert and never updated (the recapture creates a NEW Screenshot, not updates the existing one — verified by reading `recapture.sh` flow). So `capturedAt` IS the lifetime marker. Good.
- **Pin level** (`route.ts:38`): `where: { updatedAt: { gt: since } }` — correct. Pin's `updatedAt` is bumped when a comment is added (the reopen-on-reply code at `comments/route.ts:46-48` does `prisma.pin.update({ ..., data: { status: 'OPEN' } })`, which bumps `updatedAt`). Good.
- **Comment level** (`route.ts:42`): `where: { updatedAt: { gt: since } }` — correct. Comments have an `updatedAt`.
- **Client-side** (`DashboardProjects.tsx:31-44`): the `lastSuccessfulPoll - 1000` overlap is the right shape. The 1-second overlap catches same-tick writes. The 5s polling interval, the `document.hidden` skip, the `mountedRef` cleanup — all correct. The cursor update happens AFTER `setProjects(data)` (line 38-44), so a slow response can't drop a write that landed during the response serialization.

**Test coverage:** `tests/integration/projects-since.test.ts` has 5
tests (probably the 3-polls-then-4th-empty delta test the plan called
for). The build output shows the route is compiled; the 259 baseline
includes these tests passing. **No regression.**

**Minor nit (not a bug):** the `since` is computed as
`new Date(sinceParam)` then `.getTime()` is never called — instead
prisma gets a Date object directly. Works, but `new Date('garbage')`
returns an Invalid Date, and `Invalid Date > Real Date` is `false`
(NaN comparisons), so a `?since=garbage` param would just trigger
the fallback "return the full tree" path (line 22: `filterSince =
sinceParam && !Number.isNaN(since!.getTime())`). Defensive, but
not documented. Not a bug.

## Verdict

**The codebase is NOT ready for P1 work as-is.** Three of the four
R0.3 fix cards (A1, A3, A4) are pure 5-10 LOC one-route edits that
close known 500/422 leaks; shipping the new R1.2 CSRF middleware
without first closing A1 and A3 would mean the new CSRF layer
guards the wrong inputs. A2 needs a new `validatePinId` /
`validateProjectId` function added to the lib, which is a small
expansion of the R0.3 surface but well within the same ticket.
**Recommendation: ship the 4 fix cards as a single "R0.3 closeout"
patch (≤1 day), get the 259 baseline still green, then start P1 in
the order the plan dictates (R1.3 → R1.2 → R1.1).** The P0
foundation itself (R0.1 / R0.2 / R0.3-where-wired) is solid — the
build is green, all 259 tests pass, and the 3 R0 commits show no
regression. The blocker is *R0.3's incomplete rollout*, not the
P1 work itself.
